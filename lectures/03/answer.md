- 実装済み：確認問題 `make_quiz` と、承認付き学習記録保存 `save_learning_log`。
- 検証範囲：作成支援環境の模擬モデル検証に加え、本人のCodespacesでGemini実APIによる保存の承認・拒否を実行した。両者の結果を分けて記録する。

## 演習

### 第1回の素のLLMとエージェントの違い

設計上、単発のLLMは入力された質問へ直接回答する。一方、エージェントは、モデルが選んだツールをプログラムが実行し、その返り値をモデルへ渡して回答を作る。
本実装には用語集検索、講義要約、確認問題、学習記録保存の4ツールがある。

同じ質問をGeminiの単発呼出し・エージェント呼出しで比較する実験は未実行である。したがって、回答の正確性が向上したとは実測結果として主張しない。

### 追加したツールとdocstring

| ツール | 引数 | 説明に記載した利用場面 |
| --- | --- | --- |
| make_quiz | lecture: int | 「第2回の確認問題を出して」のように復習問題を求められたとき |
| save_learning_log | topic: str, learned: str, next_step: str（省略可） | 利用者が学習記録の保存を依頼したとき。説明・閲覧だけでは使わない |

`make_quiz`は、指定回の用語集から1項目を選び、問題と定義をJSONで返す。存在しない回（0等）では、その旨の文字列を返し、例外で落ちない。

### traceで確認した呼出し

`uv run python -m scripts.verify_lec03`で、モデルのツール選択と利用者入力を固定した再現検証を実行した。
モデルは外部APIを使わない `FunctionModel / scripted-offline-model`。保存本体・承認待ち・履歴を使う再開は、実際のPydantic AIの処理である。

```text
[tool call] make_quiz({'lecture': 2})
[tool call] save_learning_log({'topic': 'LoRA', 'learned': '基盤モデルを固定し追加行列を学習する。', 'next_step': '用語集を読み直す。'})
```

確認問題のモデル呼出しは2 requests（ツール要求→結果受信後の応答）。保存も、最初の要求1回と承認・拒否を渡した再開後1回の計2 requestsだった。
これらは模擬モデルへの呼出し回数であり、Geminiでも必ず同じ回数になるという意味ではない。模擬モデルのusageにあるトークン数も、Geminiの実トークン数として扱わない。

原文：`offline_trace.txt`。構造化結果：`offline_result.json`。

## 宿題

### 選んだ理由とやったこと

セキュリティ監視の実務でも、情報を確認する処理と、ファイル保存や設定変更など状態を変える処理では、必要な確認が異なる。今回の学習支援エージェントでも、説明・検索はそのまま行い、保存は利用者が内容を確認してから実行する設計を試した。

1. `app/tools.py`に`save_learning_log`を実装。テーマ・学んだ内容・次に学ぶこと・UTC保存日時をJSONとして`learning_log/`へ新規保存する。
2. `app/agent.py`で`agent.tool_plain(..., requires_approval=True)`として登録。
3. `Agent`の`output_type`を`[str, DeferredToolRequests]`にし、ツール本体の実行前に一度停止する。
4. CLIで保存予定の引数全文を表示し、`y`または`yes`と回答された呼出しだけ承認する。
5. `DeferredToolResults.approvals`へtool_call_idごとの判断を設定し、`message_history=result.all_messages()`とともに実行を再開する。
6. 拒否・空入力・EOF・Ctrl+Cでは保存しない。承認要求の繰返しとモデル呼出しには上限を設ける。

承認の判断はモデルへ生成させず、CLIが利用者から取得する。指示文に「確認すること」と書くだけではなく、フレームワークの実行停止を使った。

### 検証結果

作成支援環境で2026年11月7日に確認した結果。利用者入力は再現検証用に注入したものであり、人が確認画面を操作した記録とは区別する。

| ケース | 承認前のファイル数 | 再開後 | 確認結果 |
| --- | ---: | ---: | --- |
| 模擬入力 y | 0 | 1 | 承認後のみJSONを新規保存、内容も引数と一致 |
| 模擬入力 n | 0 | 0 | ツール返り値のoutcomeはdenied |
| 模擬入力 空文字 | 0 | 0 | 未回答を承認として扱わない |
| make_quiz(2) | 0 | 0 | 承認なしで確認問題を返し、記録は作らない |

保存先は一時フォルダへ差し替え、検証終了時に破棄した。個人の学習ログは公開していない。

`uv run --frozen pytest -q`：**34 passed in 4.92s**（既存11件＋追加23件）。承認前の無書込み、承認後の保存、拒否、空入力、EOF・Ctrl+C、複数呼出しの個別承認、承認要求の繰返し停止、保存失敗、入力検証、読取りツール、ツール一覧等を確認した。

`uv run python -m app.agent --list-tools`：4個のツールとdocstring・引数が表示されることを確認。APIキーは不要だった。

### 保存と公開の扱い

- 保存先とファイル名をモデルから受け取らず、`learning_log/`とUUIDで作る固定構成にした。
- 新規作成モードで開き、既存記録を上書きしない。
- 空のテーマ・本文、長すぎる入力、保存先フォルダのシンボリックリンクを拒否する。
- `learning_log/`は既存の`.gitignore`に含まれ、`git check-ignore learning_log/example.json`で対象であることを確認した。
- 承認は通常のエージェント呼出しに適用される。Pythonコードから保存関数を直接呼ぶ場合のアクセス制御や、OSの権限管理を代替する仕組みではない。

### 気づき・疑問とセキュリティ×AIへの考察

モデルが「保存するツールを選ぶこと」と、利用者が「保存を許可すること」は別の判断である。`DeferredToolRequests`で停止した時点ではファイルが存在せず、承認の後に初めて保存されることを実ファイルで確認できた。

難しかった点は、承認待ちの出力を通常の回答文字列と区別し、tool_call_idと会話履歴を対応させて再開することだった。また、拒否時も保存成功のように扱わず、モデルへ拒否の結果を返す必要がある。

実務へ応用するなら、モデルが提案する調査結果の保存やチケット更新を、人が確認する設計が考えられる。ただし本課題では学習記録の保存のみを扱い、実際の業務システムの操作はしていない。

承認画面があるだけで内容の正確性や機密情報の保護まで保証されるわけではない。保存内容を確認できる表示、操作権限、公開対象の制御を組み合わせる必要がある。また、Gitの除外設定は既に追跡済みのファイルや強制追加まで防ぐものではない。

### 本人のCodespacesによるGemini実API確認（2026-11-07）

使用モデルは起動表示の `gemini-3.5-flash-lite`。本人の実行ログから以下を確認した。

| 操作 | 実際の結果 |
| --- | --- |
| `uv sync --frozen` | 76 packagesを確認、依存関係は変更なし |
| `uv run pytest -q` | **34 passed in 10.57s** |
| LoRAの学習内容を指定して保存を依頼 | `DeferredToolRequests`で停止し、topic・learned・next_stepの確認画面を表示 |
| `y`で承認 | `[approval] approved`。その後503で最終回答は得られなかったが、別コマンドで**LoRAのJSONが1件保存済み**であることを確認 |
| もう一度保存を依頼し、`N`で拒否 | `[approval] denied`。traceの保存ツール返り値は `The tool call was denied.`。最終回答でも保存を行わなかったと説明 |
| 拒否後のファイル件数を確認 | 補助コマンドの余分な閉じ括弧によりSyntaxError。件数はこの時点では未確認であり、1件のままと実測したとは記載しない |

承認後に確認した保存日時は2026-11-07T04:27:38.652628+00:00（日本時間13:27:38）。個人の学習ログ本体・ファイル名は公開せず、保存件数と成功の事実を記録した。

拒否ケースのtraceでは、次の2ツールが要求された。

```text
[tool call] search_glossary({'query': 'LoRA'})
[tool call] save_learning_log({...})
[tool return] save_learning_log -> The tool call was denied.
[usage] input_tokens=2681, output_tokens=203, requests=3, tool_calls=1
```

save_learning_logの引数はtopic・learned・next_stepだった。学習内容の本文は個人の記録に当たるため、上記抜粋では省略した。拒否された保存は実行されないため、2件のtool call表示に対して、usageのtool_callsは実行された検索の1件となっている。

模擬モデルでは2 requestsだったのに対し、この実APIの拒否ケースは検索も含めて3 requestsだった。モデルの選択によって呼出し順と回数が変わることを確認した。承認ケースは503で終了しusageが表示されていないため、呼出し回数・トークン数は不明として扱う。

### 実APIで得た気づき

承認後の503表示だけでは、保存が失敗したとは判断できなかった。実際にJSONは1件存在していたため、「保存という副作用の完了」と「モデルの最終回答の成功」を分けて扱う必要がある。失敗表示を見て保存を無条件に再実行すると、UUIDによる別ファイルとして二重保存される可能性がある。今後の改善として、ツールの保存成功を最終回答とは別に表示し、再実行時の重複を防ぐ設計が考えられる。これは今回の実装では未対応である。

また、モデルが保存予定の学習内容を補完する場合があるため、承認画面ではテーマだけでなく本文と次の学習予定まで確認する必要がある。
