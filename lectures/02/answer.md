## 宿題

### 変更したデータ

講座公式ノートブックを基に、FAQ・GROUNDED・UNGROUNDEDを独自題材へ置換した。
JSONの形式（answer:文字列 / needs_review:真偽値）を維持する。

| FAQ項目 | 架空の訓練規則 |
| --- | --- |
| 不審メール | 開かず、訓練窓口へ報告する |
| 調査ログ | 原本を保存し、コピーで分析する |
| 重要度 | 影響と緊急度で判断する |
| 端末隔離 | 責任者の承認後に実施する |
| 引継ぎ | 事象と対応状況を記録する |

これらは課題専用の架空規則であり、実在組織の手順ではない。

### 根拠なしの質問の作り方

FAQの話題には近いが、値・製品・具体的手順が書かれていない質問を用意した。
例：「調査ログの保存期間は何日ですか」「承認後に隔離する際の製品名は何ですか」。
FAQだけでは答えが定まらないため、needs_review=trueで確認を求めるのが正解となる。
また、FAQにない担当者名・通報期限・暗号方式を問う追加質問を用意し、FAQにある隔離承認の質問を対照とする。

学習14件（根拠あり10・なし4）、検証7件（あり5・なし2）、評価21件（あり15・なし6）。
質問文を分割間で重複させず、評価時はFAQと質問だけをモデルに渡す。
同じFAQを共有しているため、未知の運用規則に対する汎化を測る実験ではない。

### 考察（実行前の設計上の考察）

LoRAは基盤モデルを固定し、追加行列を学習する。JSONの出力形式や確認要求の答え方を揃える用途に適している。
一方、変更される規則や案件固有の情報を重みに覚えさせ、最新性まで保証する用途には向かない。
検索で根拠を提示する仕組みと、形式を学習させる仕組みを分けて設計することが考えられる。

本実験は毎回FAQを入力しており、改善しても「知識を重みに暗記した」とは結論できない。
内容正解率は確認要否と必須語句による自動採点のため、否定や余分な断定を原文で確認する。
形式の妥当性・根拠の妥当性・自動実行の権限は別に管理し、needs_review=falseだけで遮断などを実行しない。
