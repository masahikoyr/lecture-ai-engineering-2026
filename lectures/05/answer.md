**実装・自動テスト・実APIでの3問×2方式の比較を完了。Codespacesの実測結果と、取得本文に照らした回答・引用の確認結果を以下に記録した。**

## 演習

第5回の配布コード・教材・検索DBを確認し、通常のベクトル検索と前後ページ追加を実APIで実行した。全文投入・Tree・Graphの比較は未実施であり、今回の宿題では取得処理の改良に取り組んだ。講義のデモ数値を自分の実測値として転記していない。

全文投入は全9資料・438ページ、他の3方式は第1〜3回本講義・214ページが対象であり、このままでは厳密な方式比較にならない。宿題では、同じ214ページを対象とする通常検索と前後ページ追加を比較する。

## 宿題

### 1. 取り組んだレベル・目的

**実装（Implementation）**。検索したページの前後1ページも返すよう取得処理を改良した。単一ページだけでは欠ける説明を補えるか、不要な情報がどれほど増えるかを確かめる。

セキュリティ監視でも、ログの前後を読むと経緯が分かる一方、別のホストや無関係なログを混ぜると誤解につながる。同様に、資料の前後を補うときも「どの資料の何ページか」という境界と出典を保つ設計にした。

### 2. 変更した内容

| ファイル | 変更・役割 |
|---|---|
| `app/retrieval.py` | `add_neighbor_pages()`を追加。`search(..., include_neighbors=True)`で切り替える |
| `app/tools.py` | 通常版と前後追加版に同じエラー処理を使う |
| `app/agent.py` | `--neighbors`を追加。モデルへ渡すツール名・説明・引数と指示文を通常版とそろえる |
| `scripts/compare_lec05.py` | 実APIで3問×2方式を比較し、回答・取得ページ・時間・usage・費用をJSONへ保存する |
| `scripts/verify_lec05.py` | 固定した検索ヒットからの展開を実教材で検証する。APIは使わない |
| `tests/test_neighbor_retrieval.py` | 資料境界、重複、欠番、実SQLite検索、ツール配線、比較記録・再開処理を検証する |

取得処理の規則：

1. 通常検索の上位5件と順位をそのまま残し、最初に並べる。
2. `load_pages()`の情報から、同じ`document_id`、PDFページ番号が±1のページを探す。同じ資料なら章の境界を越えて補う。
3. ページIDで重複を除き、元のヒットも含めて各ページを一度だけ返す。欠番の先には飛ばない。
4. 本文・資料名・章・ページ番号を保持し、`retrieval_role`と`seed_page_ids`で入口と追加元を追跡する。
5. 追加ページには未計算の距離を付けない。入口の距離を追加ページの類似度として流用しない。

入口が5件なら最大15件になる。重なる範囲は重複除去される。本文・埋め込みモデル・検索件数は変えず、追加ページの取得で埋め込みAPIを呼ばないため、索引の再作成は不要。

### 3. 比較する質問と固定条件

質問と参照候補を先に[comparison_cases.json](comparison_cases.json)へ定義した。質問は講義で提示された例を使用する。

| ID | 質問の要点 | 確かめること・参照候補 |
|---|---|---|
| lora | LoRAの固定・学習対象、QLoRAが加えるもの | 第2回p.52。1ページで足りる場合の情報増加 |
| memory | コンパクションとセッションをまたぐメモリ、日々のメモ | 第3回p.13、39、40。隣接ページの追加と離れた根拠の限界 |
| unanswerable | 今回のRAGの実測平均応答時間と正答率 | 資料に今回の実測ログはない。数値を創作しないか |

実API比較では同じ質問・資料・索引・モデル・指示文・ツール仕様を使い、取得方法を切り替えた。通常は5件、追加版はその前後1ページを補う。実際のモデルは`gemini-3.5-flash-lite`、埋め込みは`gemini-embedding-001`、温度は両方0。モデル名と資料・コードのハッシュを結果に残した。

実行順は1問目「通常→追加」、2問目「追加→通常」、3問目「通常→追加」。各組1回の観察であり、統計的な優劣は結論づけない。検索語はエージェントが決めるため、同じ質問でも変わる可能性がある。引数を記録し、検索語が異なる場合は取得処理だけの効果と断定しない。

実教材から選んだ**入口1ページを意図的に固定**し、展開処理を確認した。自然文の埋め込みによる上位5件検索でも、Geminiの回答比較でもない。

詳細は[offline_result.json](offline_result.json)。`local_expansion_seconds`は固定ヒットの展開処理だけの時間で、検索・埋め込み・生成を含む回答時間ではない。文字数は本文だけで、トークン数には換算していない。回答・トークン数・生成費用は`null`（未計測）で、0円・0トークンの実測を意味しない。

役立つ例と残る制約：

- **追加できた根拠：** 第3回p.39の前後を補うとp.40が入り、日々のメモをすべて長期メモリに移すわけではないという説明を参照できた。固定ヒットでの取得段階の改善であり、実APIの観察とは区別する。
- **不要な情報の増加：** LoRAの説明はp.52にある。前後も返すと本文が1,239文字増えた。p.51は補足説明、p.53はFTと知識の話で、今回の質問に必須とは限らない。
- **届かない根拠：** p.39から±1ではp.13に届かない。離れた根拠には再検索やTree・Graphなどの検討が必要。
- **答えのない質問：** 周辺ページを増やしても今回の実測ログは得られない。取得件数が増えることと回答可能になることは異なる。実APIでは両方式とも数値を創作せず、確認できないと答えた。

#### ツール経路と取得したページ

- **LoRA：** 通常版は`LoRA 固定 学習 QLoRA 加える`、追加版は`LoRA QLoRA 固定 学習`で各1回検索。どちらの入口にも第2回p.51、52が入っていた。通常版5ページに対し追加版は重複なし11ページ。回答の引用先は両方p.51、52で、追加6ページは引用されなかった。
- **メモリ：** 最初の検索語は両方`コンパクション セッション メモリ`で、入口も同じ5ページ（第3回p.65、39、38、13、40）。通常版はさらに`長期メモリ 日々のメモ すべて`で再検索し、追加版は1回で回答した。追加版は11ページを取得したが、引用したp.13、38〜40、65はすべて入口にあった。追加ページが不足していた根拠を補ったと結論づけることはできない。
- **資料に答えのない質問：** 通常版は`RAG 実測 平均 応答時間 正答率`、追加版は`実測平均応答時間 正答率`で各1回検索。追加版は15ページとなり、隣接追加した第2回p.18を一般的な評価方法の助言に使った。ただし今回の実測値を答えられるようになったわけではない。

#### 改善の観察と、残る失敗・制約

メモリの質問では、検索呼び出しが2回から1回、モデル応答が3回から2回になり、入力トークン数は6,548から4,746（**27.52%減**）、生成API推定費用は**10.51%減**だった。ただし必要な根拠は両方の初回入口ですでに取得されているため、モデルが再検索を選んだ揺れと、追加本文の影響をこの1回では切り分けられない。観測上の効率改善として扱う。

一方、LoRAの入力は**83.19%増**、費用は**64.26%増**。答えのない質問では入力が**114.69%増**、費用が**70.63%増**となった。今回、誤答を修正する効果は観測されず、情報を常時増やす負担が残った。6件合計でも推定費用は通常版0.0060599 USDに対し追加版0.0076984 USDとなった。

3問とも生成した検索語やモデルの判断は完全には固定されていない。応答時間も各1回のネットワーク・サーバー状態を含む値で、短縮したケースだけから高速化を断定しない。固定ヒットの検証では隣接説明を補えることを確認したが、実APIで根拠の補完が必要な問題を追加し、検索語をそろえた複数回比較を今後行いたい。

### 6. 気づき・疑問

前後ページを加えるだけでも、資料ID・ページ番号・出典を保ち、重複を除く設計が必要だった。追加ページは検索上位のページと取得理由が異なり、距離を同じ意味で表示すると誤解につながると気づいた。

今回の用途では、前後ページを常時追加する設定は採用せず、根拠が不足したときに補う候補として考える。単一ページで足りる質問や答えのない質問では、入力と費用の増加を実際に確認したためである。必要時だけ追加する制御は今回まだ実装していない。次は必要な根拠を取りこぼす質問を増やし、条件をそろえた反復比較で判断したい。
